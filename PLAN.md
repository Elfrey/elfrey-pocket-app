# Elfrey Pocket App — план работ

> Мобильное приложение-чарлист dnd5e для Foundry VTT v13/v14 в виде standalone-страницы модуля. Документ рабочий: фазы отмечаем по мере выполнения.

## 0. Цель и рамки

**Цель.** Игрок открывает на телефоне `https://dnd.elfrey.ru/modules/elfrey-pocket-app/app.html` (на v14 — с пути вне Data, см. §8c) и получает полноэкранный чарлист своего персонажа с бросками и управлением — без канваса, сцены, токенов, штатного интерфейса и **без загрузки остальных модулей мира**. Вся логика (броски, активности, расход ресурсов, карточки чата, эффекты) идёт через штатный API dnd5e, поэтому поведение совпадает с десктопным клиентом, а серверные хуки/автоматизация мира работают как обычно.

**Входит:**
- логин прямо в приложении (свой экран вместо `/join`), выбор персонажа (если owned-актёров несколько);
- обзор: HP / temp HP / AC / скорость / инициатива / бонус мастерства / hit dice / death saves / истощение / состояния / концентрация;
- броски: характеристики, спасброски, навыки, инструменты, инициатива, death save, концентрация, hit die, произвольная формула;
- отдых (короткий/длинный) через штатные диалоги dnd5e;
- инвентарь: использование предметов/активностей, экипировка, attunement, количество, заряды, валюта, вес;
- заклинания: слоты, подготовка, каст через активности, концентрация, фильтры;
- черты/особенности, активные эффекты, состояния;
- чат: полный лог Foundry с dnd5e-карточками (Attack / Damage / Save / Apply), ввод сообщений и формул, whisper;
- PWA («на экран Домой», без адресной строки), перенаправление телефонов с обычного `/game` на приложение.

**Не входит:** карта/сцена, движение токенов, HUD токена, GM-инструменты (кроме диагностики), «тяжёлые» разделы листа (advancement / level-up, редактор биографии) — для них кнопка «Полный лист», открывающая штатный лист dnd5e в масштабированном виде.

## 1. Контекст среды (проверено по исходникам и живому серверу)

| Факт | Значение |
| --- | --- |
| Foundry | v13.351 (30013, HTTPS `dnd.elfrey.ru`), v14.367 (30014), тест **v13-test 30113** |
| dnd5e | **5.3.3 на обеих версиях** → одна кодовая база |
| Где живёт модуль | `shared-data/modules/elfrey-pocket-app/`, симлинки → `data-v13/Data/modules/`, `data-v14/Data/modules/`; `data-v13-test` видит его через общий `modules` |
| Статика модуля | `express.static(Data, {redirect:false})` — файлы из `modules/<id>/` (включая `.html`) отдаются **без сессии**; `/scripts/*.mjs`, `/systems/dnd5e/*`, `/socket.io/socket.io.js` — тоже публичны |
| Сессия | cookie `session` **не HttpOnly** (`SameSite=Strict`), читается из JS — так делает сам `foundry.mjs` (`Game.getCookies()`); анонимную сессию выдаёт `GET /join` |
| Логин | `POST /join` JSON `{action:"join", userid, password}`; 401 + текст `JOIN.ErrorInvalidPassword` / `JOIN.ErrorUserDoesNotExist` / `JOIN.ErrorBanned`; список игроков — socket `getJoinData` → `{users, world, …}` |
| Бутстрап ядра | `foundry.mjs` в конце регистрирует `DOMContentLoaded`-обработчик: `gameView = pathname.split("/").at(-1)` → `Game.create(view, session)` → `game.initialize()`. Читает глобальные `const SIGNED_EULA / ROUTE_PREFIX / MESSAGES` из inline-скрипта страницы |
| Порядок init | `init` → `registerSettings` → `i18n` → `setup` → `playlists.initialize()` → `initializeRTC()` → `initializeCanvas()` (`core.noCanvas` → выход) → `initializeUI()` → `documentIndex.index()` → `ready` |
| Данные мира | Один socket-запрос `world` — все документы мира (актёры с предметами, сцены, журналы, настройки, сообщения). У `beard` LevelDB: actors 16 MB, settings 12 MB (!), scenes 2.5, journal 2.3 — реальный JSON меньше LevelDB, но это единственный крупный трафик, и он такой же у десктопа |
| Бандлы | `foundry.mjs` 6.0 MB + `vendor.mjs` 2.2 MB + `dnd5e.mjs` 2.9 MB + `dnd5e.css` 0.5 MB до gzip (`compressStatic: true`) |

**Уже установленные мобильные модули:**

| Модуль | Подход | Вывод |
| --- | --- | --- |
| `fvtt-mobile-api` 2.0.0 (ваш, v11–12) | bridge-сервер + отдельное приложение, ручная сериализация актёра, свой `handleRoll` | Показал цену «полностью своего» клиента: всё, что умеет dnd5e, приходится переписывать. Наш вариант берёт ядро + систему целиком, но не берёт ничего лишнего |
| `mobile-companion-dnd5e` (Syrious, light) | Svelte-приложение внутри обычного клиента | Ориентир по UX (HP/temp HP, инициатива adv/dis, эффекты на себя, избранное), но грузит весь клиент со всеми модулями |
| `mobile-sheet` (theripper93, v11) | noCanvas + масштаб штатного листа | Идея для fallback «Полный лист» |
| `mobile-improvements`, `touch-vtt` | адаптация штатного UI/канваса | Не участвуют: в приложении их код не загружается вовсе |

## 2. Архитектура: standalone-страница модуля

```
телефон ──GET──▶ /modules/elfrey-pocket-app/app.html      (статика, без сессии)
   app.html: inline-глобалы (SIGNED_EULA, ROUTE_PREFIX, POCKET5E.domReady), css/foundry2.css,
             vendor-скрипты как у /game, скрытые mount-points core UI, <main id="pocket5e-root">
   boot.js:
     1. await DOMContentLoaded → import("/scripts/foundry.mjs")   ← встроенный бутстрап ядра не срабатывает
     2. localStorage["core.noCanvas"]="true"; стабы: Playlists#initialize, AVMaster#connect, DocumentIndex#index
     3. cookie session (нет → GET /join) → Game.connect(session)
     4. socket.session.userId пуст → экран логина (getJoinData + POST /join) → reload
     5. import dnd5e.css/dnd5e.mjs → import scripts/main.js (наши хуки)
        → Game.getData(socket) → new Game("game", data, session, socket) → game.initialize()
   main.js (ready) → PocketShell рендерится в #pocket5e-root; #interface скрыт CSS
```

**Что это даёт.** На телефон приходит ядро Foundry + dnd5e + наш модуль и данные мира — и ничего из остальных 100+ модулей (ни скриптов, ни стилей, ни их `init`-работы). Канвас не создаётся → нет PIXI-инициализации, текстур, освещения. При этом все броски, активности, карточки и диалоги — штатные dnd5e, т.е. «пользуемся инструментами Foundry».

**Обычный `/game` на телефоне.** Модуль включён в мире как обычно; его `main.js` в `init` определяет телефон (авто/настройка/`?mobile=`) и делает `location.replace(app.html)`. Так игрок, привычно открывший `/game`, всё равно попадает в приложение. Кнопка «Полный клиент» ставит `mode=off` и уводит в `/game`.

**Совместимость.** Бутстрап повторяет ~30 строк из `foundry.mjs` (список vendor-скриптов, глобалы, `Game.connect/getData/new Game/initialize`) — это точка привязки к версии ядра. В 13.351 и 14.367 они совпадают (проверено); при апгрейде ядра сверять `templates/views/layouts/main.hbs` и хвост `foundry.mjs`.

**Известные компромиссы.**
- Данные мира приходят целиком (так устроен `world`-запрос сервера). Для больших миров имеет смысл чистка: 12 MB `settings` у `beard` — какой-то модуль хранит там кэш; замер и список «тяжёлых» ключей — в фазе 8.
- Ядро всё равно скачивает `vendor.mjs` (PIXI) — он импортируется `foundry.mjs` статически. ~2 MB gzip-трафика один раз, потом кэш.
- Языковые файлы **активных** модулей мира всё равно подгружаются `Localization` (это данные из `game.modules`, не код) — мелкие JSON, но много запросов; при необходимости фильтруем `data.modules` перед `new Game`.
- Инициатива требует существующего боя (encounter создаёт GM).

### Фаза 10 — GM-relay: использование предметов через клиент мастера (midi-qol) 🚧 прототип (ветка `feature/midi-relay`, 2026-08-27)

**Задача владельца:** стол играет с midi-qol (+ DAE, CPR, Gambit's, Automated Animations, Sequencer/JB2A, Monk's TokenBar, LMRTFY, times-up). Хочется, чтобы использование предмета/заклинания с телефона проходило через midi «как с десктопа».

**Почему само не работает.** Приложение грузит только ядро и dnd5e — ни одного другого модуля (в этом его скорость). Midi — libWrapper-обёртка над `Activity#use`, живёт в клиенте, *начавшем* использование; на телефоне её нет → уходит ванильная карточка dnd5e, midi мастера чужие ванильные карточки не перехватывает. Грузить midi и его стек в телефон нельзя: нет канваса (`core.noCanvas`), midi опирается на `canvas.tokens`, шаблоны, `game.user.targets` (объекты Token).

**Референс — Swipe VTT (`data-v13/Data/modules/swipe-vtt`, исходники в source map'ах).** Его standalone (страница без клиента Foundry) делает то же: `emit('module.swipe-vtt', {action:'itemActivity', actorId, itemId, activityId, actionType, userId, advantageMode, rollMode, bonus, attackMode, targetIds})` → GM-обработчик (`src/standalone/StandaloneSocketHandler.mjs`) подменяет `game.user.targets` мастера на присланные токены, вызывает `activity.rollAttack/rollDamage/use(config, {configure:false}, {data:{author: userId}})`, восстанавливает цели; чат ретранслирует HTML карточек (комментарий «re-relay for message updates (e.g. midi-qol)»). Midi там работает *побочно* — ни одного обращения к его API; после `use()` они зовут `rollDamage()` (с midi — дубль урона); прав на `itemActivity` не проверяют. Цели — свой mini-canvas (~2000 строк: сетка, стены, шаблоны, движение). Лицензия CC BY-NC 4.0 — код не копируем, схему воспроизводим.

**Что сделано в прототипе.**
- `module.json`: `"socket": true`; канал `module.elfrey-pocket-app` через `game.socket` (socketlib на телефоне нет).
- `scripts/relay.js` — обе стороны протокола:
  - телефон → `{type:"use", v:1, id, userId, gmId, actorUuid, itemId, activityId, targetUuids[], advantage, disadvantage, rollMode}`; ждёт **приёма** (15 с), сам воркфлоу может идти дольше (испытания, реакции);
  - мастер → `{type:"useResult", id, ok}` после валидации, `{ok:false, error}` при отказе или падении воркфлоу (второе сообщение показывается игроку предупреждением);
  - исполняет только **назначенный мастер** — `game.users.activeGM` (ядро выбирает одного и того же на всех клиентах; v13 и v14), поэтому при двух мастерах каст не дублируется; если адресат ушёл — берёт текущий назначенный;
  - валидация на стороне мастера: пользователь существует, `actor.testUserPermission(user, "OWNER")`, предмет/активность найдены, цели — TokenDocument'ы **сцены, которую смотрит мастер** (иначе отказ «мастер смотрит другую сцену»);
  - с midi: `MidiQOL.completeActivityUse(activity, {midiOptions:{targetUuids, ignoreUserTargets:true, checkGMstatus:false, workflowOptions:{advantage, disadvantage, autoRollAttack:true, fastForwardAttack:true, fastForwardDamage:true}}}, {configure:false}, {rollMode, data:{author: userId, flags}})` — цели передаются явно, цели самого мастера не трогаются (midi сам сохраняет/восстанавливает), атака бросается сразу (никаких диалогов на экране мастера), авто-урон — по настройкам midi у мастера;
  - без midi: `activity.use({}, {configure:false}, message)` с временной подменой целей мастера (`canvas.tokens.setTargets(ids)`, есть в v13 и v14) и восстановлением;
  - автор карточки — игрок (`message.data.author`), видимость — его режим броска; флаг `flags.elfrey-pocket-app.relay.userId`.
- `scripts/shell/target-picker.js` + `templates/shell/targets.hbs` — пикер целей (bottom sheet): токены сцены активного боя (иначе активной сцены, иначе сцены с токеном персонажа), скрытые не показываются, сортировка враги → нейтральные → союзники, мультивыбор, «Без цели» / «Использовать (N)». - `scripts/bridge.js` регистрирует на телефоне обработчики под id `midi-qol` и `chris-premades` (контракты — из source map'ов midi 13.0.64 `GMAction.ts` и CPR 1.5.44 `lib/sockets.js`, `applications/dialog.js`):

  - `rollAbility`/`rollAbilityV2` → бросок **на телефоне** через dnd5e (`rollSavingThrow/AbilityCheck/Skill/ToolCheck/DeathSave`) с `advantage/disadvantage`, DC (`target`), режимом броска и нашим bottom-sheet-диалогом; через 60 с без ответа диалог закрывается и бросок делается без него (мастер ждёт бесконечно); `D20Roll` (active defence) — бросок формулы без диалога;
  - CPR `dialog` → `RemoteDialog` — рендерер дескриптора `DialogApp.dialog(title, content, inputs, buttons, config)`: button / checkbox / radio / selectAmount / selectOption / selectMany / text / number / filePicker, кнопки yesNo/okCancel/ok/cancel, результат той же формы `{buttons, <name>: value}`; `queuedDialog` (проверка потраченной реакции/бонусного действия по флагам midi + yes/no); `rollItem` → relay (use предмета целиком через `MidiQOL.completeItemUse` у мастера) с ожиданием; `remoteRoll`/`remoteDamageRolls` — оценка бросков на телефоне; `updateTargets` — no-op;
  - подгружаются языковые файлы midi и CPR (текущий язык + en) — иначе метки диалогов CPR были бы ключами.
- `relay.js` v2: ответы со стадиями `accepted` → `done`/`failed`, `awaitCompletion` (180 с), `reaction`, использование **предмета без активности** (`completeItemUse`), проброс `usage`/`dialog` (для CPR `rollItem`), `targetConfirmation:"none"` во всех relay-использованиях (окно подтверждения целей у мастера больше не всплывает).
- Побочный плюс: на любой *другой* запрос к телефону socketlib теперь отвечает `UNREGISTERED` — вызывающая сторона получает ошибку сразу, а не висит.

**Пикер целей: только видимые и в радиусе (2026-08-27, по замечанию владельца).** Телефон перед пикером спрашивает мастера (`queryTargets` → сообщение `targets`), мастер судит на своём канвасе от токена персонажа: видимость — `MidiQOL.canSee` (режимы восприятия, свет, стены; без midi — проверка стен `polygonBackends.sight.testCollision`), дистанция — `MidiQOL.computeDistance` (без midi — `grid.measurePath`), дальность — `MidiQOL.checkActivityRange(activity, token, {target})` → `normal`/`dis`/`fail` (тот же вердикт, что применит воркфлоу: reach, дальний бросок, стены; без midi — `range.value/reach/long/touch` против измерения). Пикер показывает видимых в радиусе с дистанцией; вне радиуса — за кнопкой «Показать всех видимых (N)»; невидимых не показывает вовсе. Нет токена персонажа на сцене мастера или мастер не ответил за 4 с → прежний список без проверки (с пометкой). Имена НИП — как видят игроки: у мастера через `game.hnn.getReplacementInfo` (Hide NPC Names) / `anonymous.api` (Anonymous); в запасном списке на телефоне — по флагам актёра и мировым настройкам этих модулей (`game.settings.storage.get("world")`, модули на телефоне не загружены). ## 8d. Вход не работал на v13/v14 (2026-08-26)

Экран выбора игрока грузился, но «Войти» на v13 зацикливал на логин, на v14 — «Такого пользователя нет». Две причины (обе — регрессии этой сессии, подтверждены curl):
- **v13, logout-петля:** `boot.js` `loadCoreAssets()` тянул список vendor-скриптов со страницы `/join`, а её обработчик v13 вызывает `sessions.logoutWorld(session)` — то есть каждый заход после логина разлогинивал только что вошедшего игрока (в логах — повторяющееся «Logged user out of active World»). Исправлено: запрос ассетов идёт с `credentials: "omit"` — без cookie сервер разлогинивает анонимную сессию, а не игрока; та же HTML со списком скриптов при этом отдаётся;
- **v14, поле логина:** сервер v14 читает id пользователя из тела как `userId` (в v13 — `userid`). `login.js` теперь шлёт оба поля. Проверено curl: тот же id с `userid` даёт на v14 401 `ErrorUserDoesNotExist`, с `userId` — доходит до проверки пароля.
- **v14, повторный logout после исправления:** cookie сессии на v14 — HttpOnly, `Game.getCookies()` её не видит, поэтому boot на каждой загрузке думал, что сессии нет, и снова минтил её через `/join` → logout. Заменено: сессия заводится через **`HEAD /game`** (ставит cookie, не логаутит — логаут только в `GET /join`), с `redirect:"manual"` (иначе fetch пошёл бы по 302 в `/join`; Set-Cookie из 302 применяется и без перехода). Проверено curl: `HEAD /game` ставит session-cookie на v13 и v14. `Game.connect()` на v14 без аргумента (сессия по рукопожатию WebSocket), на v13 — `connect(sessionId)`. В headless видно, что boot доходит до `wss://…/socket.io` — соединение инициируется; ответ «session» в headless под виртуальным временем не всегда доходит, это артефакт тестовой среды.

## 8c. Foundry v14: страница приложения через `public/` (2026-08-26)

Факты (проверены curl и headless Chrome): v14 отдаёт HTML из Data как `text/plain` (`Express.#n`, без настроек), SVG из Data — с CSP `script-src 'none'` (и в v13). Остальные типы (JS/CSS/JSON/PNG) чистые. Стартовую страницу из папки данных на v14 отдать нельзя.

Испробовано и отвергнуто: SVG-лаунчер с `javascript:`-навигацией (CSP), **service worker** (`sw.js` перекрашивал `app.html` в HTML, регистрировался с `/game` — у владельца страница так и не отрендерилась; причина не установлена, код убран, регистрации на устройствах снимаются при загрузке `/game`), XML+XSLT (Chrome удаляет XSLT), `blob:`/`data:` (чужой origin), реверс-прокси (инфраструктура).

**Принято: симлинк модуля в `public/` Foundry** — `public/` раздаётся без ограничений: `https://host/pocket/app.html`. Для GM — скрипты `tools/install-v14.sh` (macOS/Linux, symlink) и `tools/install-v14.ps1` (Windows, junction; под Program Files — от администратора), автоопределение папки программы (`…/resources/app` у десктопного приложения, распакованная папка у Node-сборки), повтор после каждого апгрейда Foundry. Мировая настройка «Адрес приложения» пустая = авто: v13 → `modules/…/app.html`, v14 → `pocket/app.html`; ранний редирект с `/game` использует адрес, закэшированный в браузере при предыдущем переходе (на первом заходе — редирект после `init`, когда известна версия ядра и настройка).

Различия ядра v14, учтённые в `boot.js`: cookie сессии стала **HttpOnly** (скрипту не видна) — `Game.connect()` без аргумента, сессия определяется по рукопожатию WebSocket, `new Game(view, data, socket)` (в v13 — `connect(sessionId)` и `new Game(view, data, sessionId, socket)`); ветвление по арности `Game.connect.length` / `Game.length`.

Попутно по результатам headless-тестов: `app.html` больше не хардкодит список vendor-скриптов — `boot.js` копирует стили и скрипты со страницы `/join` текущего сервера (v14 убрал `tinymce`, сменил загрузчик KTX2); `<base>` статический (динамический не учитывался preload-сканером браузера); `PIXI.Assets.init` стал некритичным (нет WebGL → предупреждение, а не падение).
